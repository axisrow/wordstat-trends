# Референс-проекты: тренды, прогноз и детекция аномалий

Ландшафт инструментов, решающих задачи, близкие к `wordstat-trends`: витрины
трендов, прогноз временных рядов, детекция аномального роста. Отдельно от
[анализа Wordstat-сборщиков](https://github.com/axisrow/wordstat-cli/blob/main/docs/REFERENCES.md),
где разобраны инструменты сбора данных.

Срез: **2026-08-20**. Проверено по метаданным GitHub API и README, не по
описаниям в поиске.

## Главное: русскоязычной ниши не существует

Поиск по GitHub (`тренды спрос россия`, `wordstat trends прогноз`,
`яндекс тренды аналитика спроса`) даёт **ноль результатов**. Витрины трендов
поискового спроса Рунета с прогнозом и детекцией аномалий на GitHub нет.

Весь существующий ландшафт построен вокруг **Google Trends**, который для
русского рынка даёт относительный индекс 0–100, а не абсолютные показы. Яндекс
Вордстат отдаёт абсолютное число запросов — это принципиально другой тип данных
и другая интерпретируемость.

## Склейка окон — задача, идентичная нашей

| Проект | ★ | Активность | Заметка |
|---|---|---|---|
| [mikedbjones/longtrends](https://github.com/mikedbjones/longtrends) | 16 | 2023-07 | Скачивает **перекрывающиеся** окна и пересчитывает их в единый ряд |

Это прямое подтверждение архитектурного решения Фазы 0. Формулировка их README:

> Google Trends limits the time period which can be downloaded using a single
> request. Each request is scaled between 0 and 100, making comparison between
> different time periods difficult. This package automatically downloads
> overlapping trends and rescales them.

У Вордстата ограничение то же по форме (окно ≤ 5 лет), но **задача проще**: он
отдаёт абсолютные показы, а не шкалу 0–100. Нам нужно только состыковать окна и
свериться в зоне перекрытия — пересчитывать шкалу не требуется. Полезно как
подтверждение подхода, не как код для заимствования.

## Прогноз временных рядов

| Проект | ★ | Лицензия | Активность | Заметка |
|---|---|---|---|---|
| [facebook/prophet](https://github.com/facebook/prophet) | 20365 | MIT | 2026-08 | Самый известный; хорош на длинных рядах с сильной сезонностью |
| [sktime/sktime](https://github.com/sktime/sktime) | 9954 | BSD-3 | 2026-08 | **Выбран для проекта.** Единый API, встроенные бейзлайны и rolling-origin валидация |
| [unit8co/darts](https://github.com/unit8co/darts) | 9498 | Apache-2.0 | 2026-08 | Прогноз + детекция аномалий в одном пакете; главная альтернатива sktime |
| [awslabs/gluonts](https://github.com/awslabs/gluonts) | 5228 | Apache-2.0 | 2026-07 | Вероятностный прогноз, уклон в глубокое обучение |
| [Nixtla/statsforecast](https://github.com/Nixtla/statsforecast) | 4875 | Apache-2.0 | 2026-08 | Быстрые классические модели; доступен через sktime как адаптер |

Почему `sktime`, а не `darts`: нужен не столько богатый зоопарк моделей,
сколько дисциплина «бейзлайн → валидация → модель». В `sktime` сезонный наивный
прогноз и `ExpandingWindowSplitter` — часть основного API, что прямо
поддерживает порядок работы из Фазы 2.

`prophet` сознательно не берём: на 60–100 месячных точках он избыточен, а его
декомпозиция менее прозрачна, чем у ETS/Theta.

**Осторожно, часто советуют мёртвое:**
[salesforce/Merlion](https://github.com/salesforce/Merlion) (4490★) и
[twitter/AnomalyDetection](https://github.com/twitter/AnomalyDetection) (3606★)
**заархивированы**. Они всплывают в статьях и ответах, но новых проектов на них
начинать не стоит.

**Позиция проекта:** для первой версии отдельная библиотека детекции не нужна.
Скор аномальности получается из уже построенного прогноза — `факт / прогноз
сезонной наивной модели`. Это интерпретируемо, дёшево и не тянет зависимость.
Специализированные библиотеки — если базовый подход упрётся.

## Ниша-поиск через LLM — то, чем мы намеренно не являемся

| Проект | ★ | Активность | Заметка |
|---|---|---|---|
| [newDevPL/GPTNicheFinder](https://github.com/newDevPL/GPTNicheFinder) | 87 | 2024-02 | Google Trends + GPT для поиска ниш; Flask-интерфейс |

Прямая иллюстрация [принципа проекта](../README.md#принцип-без-llm-только-классический-ml).
Задача заявлена похожая — поиск перспективных ниш по данным трендов — но решение
переложено на GPT: модель «генерирует идеи ниш», слоганы и промпты. Последний
push — февраль 2024, а README начинается с признания, что код сломан
обновившимися зависимостями, и предложения пользоваться вместо него платным
custom GPT.

Это ровно тот сценарий, против которого выстроен `wordstat-trends`: результат
невоспроизводим, ценность инструмента заканчивается вместе с доступом к чужой
модели, а сам код гниёт, потому что инженерной части в нём почти нет.

## Выводы для проекта

- **Русскоязычная ниша пуста.** Витрины трендов спроса Рунета с прогнозом на
  GitHub нет — ни на Вордстате, ни на чём-либо ещё.
- **Абсолютные показы против индекса 0–100.** Весь ландшафт живёт на
  относительном индексе Google Trends. Вордстат даёт абсолютное число запросов,
  что делает выводы интерпретируемее и снимает задачу пересчёта шкалы при
  склейке окон.
- **Склейка окон — известная и решённая задача** (`longtrends`), у нас она в
  более простой форме.
- **Библиотека детекции аномалий не нужна на старте** — скор выводится из
  прогноза.
- **Заброшенность — норма для этой ниши.** `pytrends` (3728★) архивирован,
  `Merlion` и `twitter/AnomalyDetection` тоже. Устойчивость и тесты ценнее
  количества фич.

## Как обновлять

```bash
gh api -X GET search/repositories -f q='google trends' -f sort=stars -f per_page=30 \
  --jq '.items[] | [.full_name, (.stargazers_count|tostring), (.pushed_at[0:10]), (.description // "-")] | join(" | ")'
```

Полезно повторять с `anomaly detection time series`, `trend detection` и на
кириллице. Проверяйте поле `archived` — в этой нише много популярных, но
мёртвых репозиториев.
